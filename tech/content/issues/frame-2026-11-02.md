## 01. 답을 기다리는 동안에도 게임은 진행된다

이동 키를 눌렀을 때 서버의 답을 기다리면 조작이 늦어진다. 먼저 움직이면 서버가 계산한 결과와 달라질 수 있다. **즉각적인 조작감과 서버의 최종 판단을 함께 유지하려면 어떻게 해야 할까?**

이 글은 서버가 이동 결과를 최종 결정하는 **서버 권위(Server Authority)** 구조를 다룬다. 클라이언트의 입력이 서버에 도착하고 응답이 돌아오기까지의 **왕복 시간(Round Trip Time, RTT)**이 120ms라고 가정하자. 초당 60번 화면을 그리면 약 7프레임에 해당한다. 입력 처리와 시뮬레이션·출력 대기는 여기에 더해질 수 있다. 이 수치는 설명용 가정이다.

대표적인 해법은 **클라이언트 예측(Client-side Prediction)**과 **서버 보정(Server Reconciliation)**이다. 예측은 자신의 입력을 서버 확인 전에 계산하는 과정이고, 서버 보정은 서버의 결과에 맞춰 클라이언트의 예측 상태를 수정하는 과정이다. [Valve의 기술 문서][src-valve]도 이 구조를 설명한다.

![그림 1. 클라이언트가 입력 101을 즉시 예측하고 102와 103을 진행하는 동안, 서버가 101을 처리한 응답이 뒤늦게 도착하는 개념 시간선.](assets/01_prediction_timeline.png)

*그림 1 · 직접 제작한 개념도. 화살표의 길이는 실제 지연에 비례하지 않으며, 서버의 후속 입력 처리는 설명을 위해 생략했다. 클라이언트는 응답을 기다리는 동안에도 다음 입력을 처리한다.*

예측 자체는 평소의 이동 코드를 먼저 실행하면 된다. 어려운 부분은 그 이후다. **뒤늦게 도착한 과거의 결과로, 이미 앞으로 진행한 현재를 어떻게 고칠까?**

## 02. 표시하던 클라이언트가 물리 규칙을 배우다

1996년 8월 2일 메일링리스트에 전재된 John Carmack의 QuakeWorld 개발 기록에는 이 변화가 선명하게 남아 있다.

이동을 먼저 계산하려면 클라이언트도 물체의 충돌 여부, 마찰, 중력을 알아야 했다. 입력을 전달하고 서버의 결과를 보여주던 프로그램 안으로 이동 시뮬레이션이 들어온 것이다. 서버는 최종 결정권을 유지하고, 클라이언트는 마지막으로 확인된 서버 상태를 바탕으로 이동을 다시 예측한다. [당시 개발 기록][src-carmack]

이 선택으로 **클라이언트의 책임이 늘어났다.** 이동을 계산하고 서버와의 차이를 고치며, 이미 보여준 결과가 바뀌었을 때의 화면 표현까지 다뤄야 했다.

당시 기록은 남은 문제도 설명한다. 자기 이동이 즉각적으로 느껴져도 같은 방식으로 예측하지 않는 문이나 발사체와의 상호작용에서는 지연이 드러났다. 무엇을 먼저 계산할 수 있는지가 설계의 범위를 결정한 셈이다. [원문][src-carmack]

### 상태를 한 단계 진행시키는 함수

이 책임을 코드의 관점에서 보자. **시뮬레이션 상태(Simulation State)**는 다음 계산의 출발점이 되는 데이터다. 이동이라면 위치뿐 아니라 속도·접지 여부처럼 이후 결과에 영향을 주는 값도 포함할 수 있다. 상태를 한 단계 진행시키는 계산은 다음과 같이 나타낼 수 있다.

$$
S_{t+1}=F(S_t,U_t,\Delta t)
$$

| 기호 | 의미 |
| --- | --- |
| `S_t` | 현재 시뮬레이션 상태 |
| `U_t` | 이번 틱에 적용할 입력 |
| `Δt` | 이번 계산에서 진행할 시간 |
| `F` | 이동·충돌 등의 규칙을 적용하는 함수 |

**틱(Tick)**은 시뮬레이션을 한 번 진행하는 단위다. 화면을 한 번 그리는 **프레임(Frame)**과 반드시 일치하지는 않는다. 여기서는 주변 환경이 변하지 않는 단순한 이동을 가정한다.

현재 상태와 입력으로 다음 상태를 만드는 것은 평소의 게임 루프와 같다. 네트워크가 들어오면 **어느 입력까지 처리한 상태인지**도 함께 알아야 한다.

Glenn Fiedler의 해설도 이 시간 차이를 짚는다. 클라이언트는 여러 입력을 적용한 상태인데 서버가 보낸 수정 정보는 그보다 과거에 대응한다. 따라서 위치 두 개를 비교하기 전에 **같은 입력 처리 지점의 상태인지**부터 맞춰야 한다. [네트워킹 해설][src-gaffer-network]

## 03. 입력 101의 답을 받았는데, 나는 이미 103까지 왔다

클라이언트가 입력 101, 102, 103을 적용했을 때 다음 서버 응답이 도착했다고 해보자.

> “입력 101까지 처리한 결과는 이 상태다.”

이 응답은 **102와 103을 적용한 결과를 포함하지 않는다.** 그 위치를 현재 위치에 그대로 덮어쓰면 후속 입력으로 진행했던 이동까지 사라진다.

아래는 직접 만든 **단순한 1차원 좌표 예시**다. 후속 입력 하나가 좌표를 1씩 증가시킨다고 가정한다. 클라이언트는 103까지 적용해 좌표가 13인데, 서버가 확인한 101 처리 후의 좌표는 10.6이다. 숫자는 원리 설명을 위한 값이며 실제 게임 측정치가 아니다.

![그림 2. 기존 클라이언트 예측은 11, 12, 13이다. 서버가 확인한 101번 입력의 상태 10.6에서 102와 103을 다시 실행하면 11.6, 12.6이 된다.](assets/02_reconciliation.png)

*그림 2 · 주황색 행에서 서버가 확인한 값은 10.6뿐이다. 11.6과 12.6은 미확인 입력을 다시 적용한 클라이언트의 예측 결과다. 좌표 차이 보정과 화면의 부드러운 표현은 별도 작업이다.*

| 처리 시점 | 기존 클라이언트 계산 | 101의 확정 상태에서 다시 계산 |
| --- | ---: | ---: |
| 101 처리 후 | 11 | **10.6 — 서버 확인** |
| 102 처리 후 | 12 | 11.6 — 클라이언트 재예측 |
| 103 처리 후 | 13 | **12.6 — 수정된 현재 예측** |

클라이언트는 다음 순서로 처리한다.

1. 서버가 확인한 101 처리 후의 상태를 기준으로 삼는다.
2. 확인된 101까지의 입력을 미확인 목록에서 제거한다.
3. 남아 있는 102와 103을 순서대로 다시 적용한다.
4. 얻어진 12.6을 현재의 예측 상태로 사용한다.

서버 위치 10.6을 현재에 그대로 적용했다면 13에서 10.6으로 크게 돌아갔을 것이다. 재실행하면 현재에 해당하는 12.6까지 계산하므로, 이 예시의 실제 수정량은 0.4다.

이처럼 **입력 재실행(Input Replay)**은 서버가 확인한 과거 상태를 현재의 예측 상태로 연결한다. 서버의 결과가 어느 입력까지 반영했는지 알아야 재실행의 시작점도 정할 수 있다. [원리 참고][src-gaffer-network]

이제 필요한 자료구조가 보인다. 클라이언트는 서버가 아직 확인하지 않은 입력을 순서대로 보관해야 한다.

## 04. 코드에는 ‘미확인 입력 목록’이 필요하다

아래는 **설명용 의사 코드(Pseudocode)**다. **고정 시간 간격(Fixed Time Step)**마다 입력 하나를 만들고 서버가 순서대로 처리한다고 가정한다. 입력 번호는 확인할 명령을 구분하는 값이며, 일반적인 구현에서 시뮬레이션 틱 번호와 항상 같은 뜻은 아니다. 최신성이 검증된 응답만 이 함수로 전달되며 패킷 손실·역전·중복 처리는 생략했다.

```text
OnLocalInput(input):
    command = { sequence: nextSequence++, input: input }

    pendingCommands.append(command)
    predictedState = Simulate(predictedState, input, fixedDt)

    SendToServer(command)


OnServerState(lastProcessedSequence, serverState):
    pendingCommands.removeAll(
        command.sequence <= lastProcessedSequence
    )

    predictedState = serverState

    for command in pendingCommands:
        predictedState = Simulate(
            predictedState,
            command.input,
            fixedDt
        )
```

`lastProcessedSequence`는 **어느 입력까지 처리한 상태인지 나타내는 경계**다. 여기서 서버의 **확인(Acknowledgement, ACK)**은 입력 처리 완료를 의미한다. 패킷을 받았다는 사실만으로는 재실행의 시작점을 정할 수 없다. Valve 문서도 처리된 명령 이후의 입력을 보관하고 다시 실행하는 구조를 설명한다. [원문][src-valve]

`Simulate`가 읽는 상태도 충분해야 한다. 위치를 복원해도 속도나 점프 상태가 잘못 남으면 이후 계산이 달라진다. 무엇을 저장할지는 그 계산이 어떤 데이터에 의존하는지 살펴 정해야 한다.

> **구현할 때**  
> **화면 스무딩(Visual Smoothing)**은 수정된 상태가 화면에서 갑자기 튀지 않도록 표현하는 처리다. 시뮬레이션의 현재 상태를 올바르게 다시 계산한 뒤, 그것을 어떻게 보여줄지 별도로 결정해야 한다.

기록과 재실행 구조가 갖춰져도 기존 이동 코드를 그대로 반복 호출해도 되는지는 따로 확인해야 한다. 그 함수 안에 소리 재생과 같은 작업이 섞여 있을 수 있기 때문이다.

## 05. 재실행은 게임 코드와 성능을 함께 건드린다

### 함정 A · 착지 소리도 다시 재생될 수 있다

이동 코드에 `이동 → 착지 판정 → 효과 생성 → 소리 재생`이 함께 들어 있다고 해보자. 서버 보정 때문에 그 입력을 다시 실행하면 효과와 소리도 반복해서 발생할 수 있다.

Valve 문서는 발소리 같은 효과의 중복을 경고하고, 해당 입력을 처음 예측할 때만 효과를 재생하는 방법을 설명한다. [원문][src-valve]

이 예시에서 시뮬레이션이 만드는 상태와 **부수 효과(Side Effect)**를 구분할 필요가 드러난다. 이후 계산에 영향을 주는 이동 상태나 탄약 수는 올바르게 복원·갱신되어야 한다. 소리와 화면 효과에는 이미 재생했는지, 취소 가능한지, 결과가 달라지면 어떻게 처리할지에 대한 정책이 필요하다.

### 함정 B · 고정 틱만으로 같은 결과가 보장되지는 않는다

**결정론(Determinism)**은 같은 초기 상태와 같은 입력에서 같은 결과를 얻는 성질이다. 고정된 `Δt`는 이를 위한 조건 중 하나다. 난수 상태, 처리 순서, **부동소수점(Floating Point)** 연산 차이도 결과에 영향을 줄 수 있다.

Fiedler의 결정론 해설은 같은 입력과 시간 간격을 적용해도 물리 솔버 내부의 처리 순서 때문에 결과가 달라지는 사례를 보여준다. 따라서 **고정 틱을 사용한다는 사실만으로 여러 환경의 동일한 결과가 보장되지는 않는다.** [Deterministic Lockstep][src-determinism]

요구 수준은 동기화 구조에 따라 달라진다. **스냅샷(Snapshot)**은 특정 시점의 상태를 묶은 데이터다. 서버 스냅샷으로 차이를 교정하는 방식과, 입력만 교환하며 각 기계가 같은 결과를 만들어야 하는 방식은 결정론에 기대는 정도가 다르다.

### 함정 C · 네트워크 지연이 재실행 비용으로 바뀐다

서버 응답이 늦어지면 다시 계산할 구간이 길어질 수 있다. 그만큼 CPU가 처리할 연산도 늘어난다. 단순한 모델로 재실행할 틱 수를 계산하면 다음과 같다.

$$
N \approx \left\lceil \frac{H}{\Delta t} \right\rceil
$$

`H`는 보정할 과거 시점부터 현재 예측 시점까지의 시간, `N`은 다시 실행할 틱 수다. 아래 숫자는 **특정 엔진의 측정값이 아닌 자체 계산 예시**다.

| 가정 | 값 | 의미 |
| --- | ---: | --- |
| 시뮬레이션 빈도 | 60Hz | 틱당 약 16.7ms |
| 다시 계산할 구간 | 120ms | 약 8틱 |
| 틱 하나의 계산 비용 | 0.4ms | 재실행 8틱이면 약 **3.2ms** |

실제 비용에는 전송 주기, 지연 시간이 흔들리는 **지터(Jitter)**, 예측 여유, 대상 오브젝트 수가 영향을 준다. **유니티(Unity)**의 Netcode for Entities 1.5.1 문서도 보정 과정에서 예측 시스템이 한 렌더 프레임 안에 여러 틱 실행되며 상당한 부담이 될 수 있다고 설명한다. [예측 실행 문서][src-unity]

따라서 실행 한 번의 비용뿐 아니라 **한 프레임 안에서 몇 번 실행되는가**도 관찰해야 한다.

### 주변 물체의 과거 상태는 어디에 있을까?

앞의 예제는 주변 환경이 변하지 않는다고 가정했다. 실제로는 이동 플랫폼, 내가 밀었던 상자, 다른 플레이어의 위치가 결과에 영향을 줄 수 있다. 이 경우 내 캐릭터와 입력만 복원해도 충분한지 검토해야 한다.

**언리얼 엔진(Unreal Engine, UE)**의 Networked Physics 문서가 설명하는 **재시뮬레이션(Resimulation)** 모드는 물리 상태 이력을 보관한다. 대응하는 과거 프레임의 서버 상태와 비교하고, 필요하면 보정 후 현재까지 다시 계산한다. 이력과 재계산에는 메모리·CPU 비용이 들며, 결과의 화면상 튐을 완화하는 표현 처리도 있다. [Networked Physics][src-ue-physics]

결국 비용을 판단하려면 재실행의 범위를 알아야 한다. ‘되감기’라는 표현을 만났을 때 무엇을 되돌리는지 먼저 확인해야 하는 이유다.

## 06. ‘되감기’라는 이름 아래 서로 다른 작업이 있다

**롤백(Rollback)**은 저장한 과거 상태로 되돌리는 과정이다. 네트워크 게임에서는 뒤늦게 받은 정보로 그 이후를 다시 계산하는 구조와 함께 사용된다. 어떤 정보가 도착했고 어디까지 다시 계산하는지에 따라 필요한 상태와 비용이 달라진다.

대표적인 구현 사례인 **GGPO(Good Game, Peace Out)**는 상대 입력 예측과 롤백을 다루는 네트워킹 라이브러리다. [개발자 저장소][src-ggpo-repo] 또 다른 사례인 **지연 보상(Lag Compensation)**은 통신 지연을 고려해 판정하는 기법이다. 여기서는 Source의 과거 상대 상태를 이용한 사격 판정을 비교한다.

![그림 3. 클라이언트 이동 보정, GGPO 롤백, 서버 지연 보상이 어떤 정보를 기준으로 무엇을 되돌리는지 비교하는 세 개의 카드.](assets/03_rewind_comparison.png)

*그림 3 · 직접 제작한 비교 도식. GGPO는 특정 롤백 구현 사례다. 롤백이라는 일반 개념을 특정 네트워크 연결 방식으로 한정하지 않는다.*

| 사례 | 뒤늦게 알게 된 정보 | 다시 수행하는 작업 |
| --- | --- | --- |
| **클라이언트 이동 보정** | 서버가 확인한 과거 상태 | 그 상태에서 미확인 로컬 입력을 적용해 현재를 계산 |
| **GGPO 롤백** | 실제로 도착한 상대 입력 | 추정 입력을 교체하고 과거 게임 상태부터 재실행 |
| **Source의 사격 지연 보상** | 사격 요청과 판정할 과거 시점 | 상대의 과거 상태로 판정하고 현재 상태로 복원 |

GGPO는 아직 도착하지 않은 상대 입력을 추정해서 진행한다. 실제 입력이 다르게 도착하면 과거 상태를 불러와 올바른 입력으로 다시 실행한다. 공식 소개는 이를 위해 결정론적인 시뮬레이션, 상태 저장·복원, 화면을 그리지 않고 한 프레임을 진행하는 기능을 요구한다. [GGPO 공식 소개][src-ggpo]

Source의 **소프트웨어 개발 키트(Software Development Kit, SDK)**에 공개된 지연 보상 코드에서는 서버가 판정할 과거 시점을 구해 상대 상태를 되돌린다. 네트워크 지연뿐 아니라 화면을 부드럽게 이어 보여주기 위한 **보간(Interpolation)**의 시간, 보상 가능 범위, 클라이언트가 보낸 시간과 측정값의 차이도 검사한다. 과거 상태를 사용할 때에도 **어느 시점의 정보를 신뢰할지**에 대한 규칙이 필요하다. [공개 구현][src-source-sdk]

따라서 ‘롤백 지원’만으로 전체 월드를 저장한다거나 모든 프레임을 다시 계산한다고 판단할 수 없다. **복원 대상과 재실행 범위**를 확인한 뒤 엔진의 자료구조와 실행 경로를 읽어야 한다.

## 07. 엔진 문서에서 기록·확인·재실행을 찾아보기

앞의 의사 코드에서 `pendingCommands`가 맡던 역할이 실제 엔진에서는 어디에 있을까? 언리얼의 **캐릭터 이동 컴포넌트(Character Movement Component, CMC)** 문서는 기록과 서버 보정을 다음 이름으로 연결한다.

| 이름 | 구조를 읽는 관점 |
| --- | --- |
| `FSavedMove_Character` | 클라이언트가 수행한 이동을 어떤 데이터로 기록하는가 |
| `SavedMoves` | 서버의 확인과 보정에 사용할 기록을 어디에 두는가 |
| `ClientUpdatePositionAfterServerUpdate` | 서버 수정 정보를 언제 반영하는가 |

Epic 문서는 로컬 이동을 기록·전달하고, 서버의 확인이나 수정 결과에 따라 저장된 이동을 다시 따라가는 흐름을 설명한다. 함수를 찾은 다음에는 **기록에 어떤 값이 들어가는지, 확인된 기록을 언제 버리는지, 어떤 경로로 재실행하는지**를 따라가면 된다. [Character Movement 문서][src-ue-movement]

유니티의 Netcode for Entities에서는 `PredictedSimulationSystemGroup`으로 예측 시뮬레이션의 실행 범위를 만날 수 있다. 문서는 적용된 스냅샷 시점부터 예측 목표 시점까지 시뮬레이션을 진행하는 구조를 설명한다. 이 그룹 안의 시스템을 분석할 때에는 실행 한 번의 비용과 한 프레임의 반복 횟수를 함께 살펴볼 수 있다. [Netcode for Entities 1.5.1][src-unity]

두 엔진을 같은 구현으로 취급할 필요는 없다. **상태·입력·확인 경계·재실행 범위**를 먼저 찾으면, 서로 다른 이름을 가진 코드가 어떤 문제를 해결하는지 비교할 수 있다.

## 08. 오늘 얻어갈 것

처음의 질문에 대한 답은 이렇다. **내 입력을 클라이언트에서 먼저 계산하기 때문에 캐릭터가 즉시 반응한다. 서버의 결과가 도착하면, 서버가 확인한 과거 상태에서 미확인 입력을 다시 적용해 현재를 맞춘다.** 통신 지연은 남아 있고, 클라이언트는 그동안의 반응과 이후 수정을 책임진다.

### 이해해야 할 네 가지 원리

1. **상태에는 입력 처리 지점이 붙어야 한다.** 서버의 101 처리 후 상태와 클라이언트의 103 처리 후 상태를 같은 시점처럼 비교하면 후속 이동을 잃는다.
2. **보정은 과거의 기준을 현재까지 연결하는 계산이다.** 확인된 입력을 제거하고 남은 입력을 순서대로 다시 적용한다. 재실행으로 만든 현재 상태도 아직 서버가 모두 확인한 결과는 아니다.
3. **재실행할 수 있으려면 의존 상태와 부수 효과를 다뤄야 한다.** 속도·점프 상태·관련 물체처럼 계산에 필요한 데이터를 복원하고, 소리·화면 효과의 중복과 취소 정책을 별도로 정한다.
4. **비용은 틱 하나의 작업량과 반복 횟수에서 함께 나온다.** 확인이 늦어지고 복원·재실행 범위가 커지면 저장 공간과 연산량도 늘어날 수 있다. 화면 스무딩은 계산 결과를 보여주는 별도 단계다.

### 코드와 프로파일러에서 확인할 지점

실행 시간과 호출 횟수를 측정하는 **프로파일러(Profiler)**를 켜거나 코드를 읽을 때에는 다음처럼 구체적인 증거를 찾아보자.

| 확인할 지점 | 실제로 볼 것 |
| --- | --- |
| **입력 기록과 서버 확인 경계** | 서버가 처리한 번호가 갱신될 때 확인된 입력만 제거되고, 미확인 입력의 순서가 유지되는가? |
| **복원하는 시뮬레이션 상태** | 위치 외에 속도·접지 상태 등 `Simulate`가 읽는 값도 올바른 시점으로 돌아가는가? |
| **재실행과 부수 효과** | 같은 입력 번호를 재실행했을 때 소리나 효과가 중복 발생하지 않도록 어떤 정책을 적용하는가? |
| **한 프레임의 총 예측 비용** | 지연 조건을 바꿨을 때 예측 시스템의 호출 횟수, 틱당 비용, 프레임당 총비용이 각각 어떻게 변하는가? |

### 자기 확인 질문

클라이언트는 입력 104까지 예측했다. 서버가 **102까지 처리한 좌표 11.4**를 보내왔고, 남은 입력은 각각 좌표를 1씩 증가시킨다. **어떤 입력을 다시 실행해야 하며, 수정된 현재 좌표는 얼마일까?**

<details>
<summary>답과 이유 보기</summary>

102까지의 입력은 이미 서버 상태에 반영됐으므로 목록에서 제거한다. **103과 104만 순서대로 재실행**하면 `11.4 → 12.4 → 13.4`가 된다. 수정된 현재 좌표는 **13.4**다.

102를 다시 적용하면 한 입력을 중복 반영한다. 반대로 11.4를 현재 좌표로 그대로 쓰면 103·104의 이동을 잃는다. 서버가 확인한 값은 11.4이며, 13.4는 그 상태에서 다시 계산한 클라이언트 예측이다.
