# 체력만 읽는데 왜 좌표까지 캐시에 들어올까요?

겜붕이의 노트 · by TeamHJD

<!-- article -->

## 화면에는 체력만 필요한데 메모리는 무엇을 읽을까요?

적 1,024명의 체력 게이지를 갱신한다고 생각해 보겠습니다. 이번 프레임에는 위치도, 속도도 바뀌지 않습니다. 그런데 객체마다 체력과 좌표를 같은 구조체에 묶어 두었다면, CPU는 체력에 접근하면서 주변 필드가 있는 메모리 구간도 함께 캐시에 가져올 수 있습니다. **체력 4바이트만 필요할 때도 이런 일이 생기는 이유는 무엇일까요?**

열쇠는 **캐시 라인(Cache Line)**입니다. CPU는 메모리에서 데이터를 가져올 때 보통 개별 `float` 하나가 아니라 일정 크기의 연속된 블록을 캐시에 채웁니다. 오늘은 계산을 분명히 하려고 **캐시 라인이 64바이트이고 배열 시작 주소가 그 경계에 정렬되어 있다**고 가정하겠습니다. 모든 CPU가 똑같다고 주장하거나, 실제 캐시 미스 횟수를 측정한 값은 아닙니다.

## 객체별로 묶는 방식과 필드별로 묶는 방식

구조체 배열(Array of Structures, **AoS**)은 객체의 데이터를 한 덩어리로 저장하는 방식입니다. 예를 들어 적 한 명이 위치 2개, 속도 2개, 체력 1개, 나머지 수치 3개로 이루어져 있고 모두 4바이트 `float`라면 한 객체는 정확히 **32바이트**입니다. 객체를 1,024개 저장하면 `32 × 1,024 = 32,768`바이트, 즉 **32KiB**입니다.

반면 배열 구조체(Structure of Arrays, **SoA**)는 `posX[]`, `posY[]`, `hp[]`처럼 필드별 배열을 따로 둡니다. 체력만 훑는 작업에서는 `hp[]` 하나를 순서대로 읽을 수 있지요. 체력 배열만 따지면 `4 × 1,024 = 4,096`바이트, 즉 **4KiB**입니다. *전체 객체 데이터가 4KiB로 줄었다는 뜻은 아닙니다.* 같은 필드를 더 촘촘하게 모은 것입니다.

이런 배치를 **데이터 지역성(Data Locality)**이라고 설명할 수 있습니다. 다음에 읽을 값이 방금 읽은 값 가까이에 놓여 있으면, 이미 가져온 캐시 라인을 활용하기 쉬워집니다. C++ 표준 작업 초안은 `std::vector<T>`가 `bool`을 제외하면 연속 저장 컨테이너임을 규정합니다. 따라서 아래 예제에서는 `vector`의 순차 배치를 전제로 설명할 수 있습니다. [C++ 작업 초안 · vector 개요](https://eel.is/c++draft/vector.overview)

## 8명만 놓고 64바이트 한 줄을 펼쳐 봅시다

AoS에서 32바이트짜리 객체 **두 개**가 64바이트 한 줄에 들어갑니다. 그중 실제로 필요한 체력은 객체마다 4바이트이므로 한 줄에 **유용한 체력 8바이트**만 있습니다. 여덟 명의 체력을 읽으려면 정렬 조건 아래 **네 줄**에 걸쳐 접근합니다.

SoA에서는 체력 여덟 개가 `8 × 4 = 32`바이트입니다. **한 줄** 안에 모두 들어갑니다. 도식에서 강조한 칸은 실제로 읽는 체력 값입니다.

![64바이트 캐시 라인 네 개에 객체 두 개씩 저장한 AoS와 한 라인에 체력 여덟 개를 모은 SoA 비교](assets/aos-soa-cacheline.svg)

*그림 1 · 직접 제작한 개념도입니다. 객체당 32바이트, 체력당 4바이트, 라인당 64바이트, 라인 경계 정렬이라는 가정 아래 필드의 배치를 보여줍니다. 실제 CPU 추적 화면이 아닙니다. 연속 배열과 청크별 컴포넌트 배열의 구조는 [C++ 작업 초안](https://eel.is/c++draft/vector.overview) 및 [Unity Entities 공식 문서](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/concepts-archetypes.html)를 참고했습니다.*

여기서 1,024명으로 늘려 볼까요? 체력만 한 번씩 순차 접근하는 이상적인 배치에서 AoS는 **512개 라인(32KiB 영역)**, SoA 체력 배열은 **64개 라인(4KiB 영역)**에 걸칩니다. 주소 범위에 포함되는 라인의 개수로 보면 8배 차이입니다.

![같은 1024개 체력 읽기에서 AoS 512개 라인과 SoA 64개 라인을 비교한 비례 막대 도식](assets/cacheline-counts.svg)

*그림 2 · 직접 계산한 저장 배치별 라인 수입니다. AoS는 1,024×32÷64=512, SoA 체력은 1,024×4÷64=64입니다. **프레임 시간이나 캐시 미스를 8배 개선했다는 실측 결과가 아닙니다.** 정렬·접근 패턴·캐시 상태에 따라 실제 성능은 달라집니다.*

## C++17에서 두 표현을 그대로 따라가겠습니다

아래는 **표준 C++17 실행 예제**입니다. 32바이트 배치가 성립하는지 `static_assert`로 검사하며, 두 방식 모두 체력 합계가 `102400`이 되는지 확인합니다. `std::vector`의 순서대로 순회할 뿐 성능을 측정하거나 벤치마크 결과를 출력하지는 않습니다.

```cpp
#include <iostream>
#include <vector>

struct Actor {
    float posX, posY;
    float velX, velY;
    float hp, shield, score, stamina;
};

static_assert(sizeof(float) == 4, "The example needs 4-byte float");
static_assert(sizeof(Actor) == 32, "The example needs 32-byte Actor");

int main() {
    constexpr int N = 1024;

    // AoS: 한 객체의 모든 필드를 인접 배치
    std::vector<Actor> actors(N);
    for (auto& actor : actors) {
        actor.hp = 100.0f;
    }

    // SoA의 체력 필드: 같은 필드를 연속 배치
    std::vector<float> hp(N, 100.0f);

    float sumAoS = 0.0f;
    for (const auto& actor : actors) {
        sumAoS += actor.hp;
    }

    float sumSoA = 0.0f;
    for (float value : hp) {
        sumSoA += value;
    }

    std::cout << sumAoS << " " << sumSoA << "\n";
}
```

```text
102400 102400
```

이 코드는 **배치의 차이**를 보여주는 예제입니다. 실제로는 `std::vector` 시작 주소가 반드시 64바이트 정렬된 것은 아니므로, 배열 양 끝의 라인 수가 그림과 다를 수 있습니다. 또한 컴파일러의 자동 벡터화, 프리페치, 작업량, 다른 데이터의 캐시 점유가 함께 영향을 줍니다. 이 두 반복문의 실행 시간만 보고 모든 게임 코드에 SoA가 낫다고 결론 내리지는 마세요.

## Unity Entities는 왜 청크 안에 배열을 둘까요?

이제 엔진에 연결해 보겠습니다. **아키타입(Archetype)**은 같은 종류의 컴포넌트 집합을 가진 엔티티를 묶는 기준입니다. Unity **Entities 1.4.8 공식 문서**는 같은 아키타입의 엔티티·컴포넌트를 **16KiB 청크(Chunk)**에 저장하고, 청크 안에 컴포넌트 타입별 배열과 엔티티 ID 배열을 둔다고 설명합니다. 각 배열의 같은 인덱스가 같은 엔티티에 대응합니다. [Unity · Archetypes concepts](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/concepts-archetypes.html) — 문서 패키지 1.4.8, 2026년 7월 생성.

이는 오늘의 SoA와 **비슷한 지역성 원리**를 활용하지만, 모든 체력을 전역 배열 하나에 모은다는 뜻은 아닙니다. 컴포넌트 배열은 **청크 단위**로 나뉘며, 아키타입마다 별도의 청크들이 존재합니다. 컴포넌트를 추가하거나 제거하면 다른 아키타입으로 옮기는 **구조 변경(Structural Change)**이 일어날 수 있고, 그 비용을 무시하면 안 됩니다.

또 다른 함정도 있습니다. Unity의 [청크 할당 문서](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/performance-chunk-allocations.html)는 비어 있는 청크나 지나치게 많은 아키타입이 메모리 낭비와 청크 사이 이동 비용을 만든다고 경고합니다. 따라서 단순히 '컴포넌트가 나뉘면 무조건 빠르다'가 아니라, **함께 순회하는 데이터가 얼마나 가까이 있는지**와 **자료를 옮기거나 관리하는 비용**을 함께 봐야 합니다.

## 언제 AoS가 더 편할까요?

UI 체력 합계처럼 한 필드만 대량으로 처리하면 SoA가 유리할 가능성이 있습니다. 반대로 매번 적 한 명의 위치·속도·체력·보호막을 전부 읽거나 객체 단위로 생성·삭제한다면 AoS의 단순한 접근과 관리가 더 적절할 수 있습니다. SoA는 여러 배열의 인덱스를 일관되게 유지해야 하며, 엔티티 삭제·재정렬에도 손이 갑니다.

우선 실제 병목이 **순회**에 있는지 확인하세요. 같은 입력과 최적화 수준의 빌드에서 AoS·SoA를 각각 측정하고, CPU 프로파일러에서 그 루프의 시간을 비교합니다. 환경이 허용하면 하드웨어 성능 카운터로 캐시 미스와 메모리 대역폭도 살펴볼 수 있습니다. CPU가 기다리는 시간에 의미 있는 차이가 없다면, 복잡도를 늘리는 전면 개편보다 현재 구조를 유지하는 선택도 합리적입니다.

## 오늘 얻어갈 것

**체력만 읽는데 좌표가 함께 캐시에 들어올 수 있는 이유는 캐시가 4바이트 필드 대신 주변의 메모리 라인을 가져오기 때문입니다.** 32바이트 AoS 객체 1,024명에서는 체력 값이 512개 라인에 흩어져 있지만, 같은 체력을 SoA로 모으면 이상적인 64바이트 정렬 조건에서 64개 라인에 걸칩니다. 이 차이는 실제 속도 향상의 보증이 아니라 **접근하는 메모리 배치의 차이**입니다.

코드에서는 객체 크기와 배열의 연속성, 필드별 접근 패턴을 확인해 보세요. Unity Entities에서는 아키타입·청크의 컴포넌트 배열과 구조 변경 빈도를 살펴보면 좋습니다. 프로파일러에서는 캐시 미스 추정보다 먼저 *해당 루프가 정말 병목인지* 확인하고, 같은 조건의 실제 시간을 비교하세요.
