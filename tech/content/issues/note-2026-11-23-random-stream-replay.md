# 같은 시드인데 왜 몬스터 등장 순서가 달라질까요?

## 시드는 같았는데 결과가 달라졌습니다

버그를 재현하려고 게임 시작 시드(Seed)를 `3`으로 고정했습니다. 어제는 첫 몬스터가 A, 두 번째가 B였는데 오늘은 이펙트 하나를 추가한 뒤 두 번째 몬스터가 달라졌습니다. **시드를 고정했는데 왜 같은 장면을 다시 만들지 못할까요?**

문제는 종종 난수의 품질이 아니라 **난수를 소비한 순서**에 있습니다. 게임 로직, 전리품, 파티클이 모두 같은 난수 생성기를 호출하면, 겉으로 관계없는 이펙트 한 번이 다음 게임 로직의 선택을 바꿉니다.

## 의사난수는 값보다 '상태의 진행'이 중요합니다

의사난수 생성기(Pseudorandom Number Generator, PRNG)는 내부 **상태(State)**로부터 다음 값을 계산하고 상태를 갱신합니다. **시드(Seed)**는 그 상태를 초기화하기 위한 입력입니다. 같은 생성기 구현, 같은 초기화 절차, 같은 호출 순서가 유지되면 같은 수열을 얻을 수 있습니다. 하지만 **시드 하나만 저장하는 것으로 실행 중 상태가 항상 복원되는 것은 아닙니다.**

숫자로 직접 살펴보겠습니다. 아래 수식은 설명만을 위한 **장난감 생성기**입니다. 실제 게임의 무작위 선택에 사용하면 안 됩니다.

```text
다음 상태 = (5 × 현재 상태 + 1) mod 16
출력 값 = 다음 상태
초기 상태 = 3
```

첫 번째 호출은 `(5×3+1) mod 16 = 0`, 두 번째는 `(5×0+1) mod 16 = 1`, 세 번째는 `6`, 네 번째는 `15`입니다. 따라서 결과 수열은 **0 → 1 → 6 → 15**입니다. 여기서 0이나 1이 무슨 몬스터를 뜻하는지는 게임의 해석이고, PRNG는 그 의미를 모릅니다.

![같은 난수 수열의 두 번째 값을 연출 이펙트가 소비하면서 이후 게임 로직의 결과가 밀리는 시간선](assets/draw-sequence.svg)

*직접 만든 개념도. 하나의 생성기를 공유하는 경우 호출을 하나 추가하면 전리품과 두 번째 몬스터에 배정되는 값이 달라집니다. 설명용 16상태 수열입니다.*

## 게임 로직과 연출의 난수 흐름을 분리하기

처음에는 게임 로직이 `몬스터1=0 → 전리품=1 → 몬스터2=6`을 소비했다고 가정하겠습니다. 여기에 게임플레이와 무관한 이펙트 난수 호출이 몬스터1 다음에 하나 들어오면 `몬스터1=0 → 이펙트=1 → 전리품=6 → 몬스터2=15`로 바뀝니다.

이럴 때 독립된 **난수 스트림(Random Stream)**을 사용합니다. 게임플레이는 상태 `3`에서 출발하는 생성기를, 연출은 상태 `7`에서 출발하는 별도의 생성기를 갖습니다. 연출 스트림은 `4 → 5`를 소비해도 게임플레이 스트림의 `0 → 1 → 6`을 건드리지 않습니다.

![게임플레이 시드 3과 연출 시드 7에서 출발한 서로 다른 난수 스트림을 나타낸 두 행의 도식](assets/stream-split.svg)

*직접 만든 개념도. 각 스트림은 별도의 상태를 보유합니다. 표시된 숫자는 설명용 생성기의 계산 결과이며 PCG32나 특정 엔진의 출력이 아닙니다.*

여기서 '분리'는 단순히 같은 생성기를 두 변수로 참조하는 것이 아닙니다. **각 인스턴스가 서로 다른 상태를 소유**해야 합니다. 또한 스트림을 분리하더라도 게임플레이 호출 순서가 달라지면 게임플레이 결과는 다시 달라집니다. 분리는 모든 비결정성을 해결하는 마법이 아닙니다.

## C++17로 호출 순서까지 확인해 보기

다음은 앞의 수식을 그대로 옮긴 **실행 가능한 C++17 검증 예제**입니다. 실제 게임용 PRNG 구현이 아니라 '누가 수열의 몇 번째 값을 소비하는가'만 검증합니다.

```cpp
#include <cassert>
#include <cstdint>

struct ToyRng {
    std::uint32_t state;

    std::uint32_t Next() {
        state = (5u * state + 1u) % 16u;
        return state;
    }
};

int main() {
    ToyRng before{3};
    assert(before.Next() == 0u); // 몬스터 1
    assert(before.Next() == 1u); // 전리품
    assert(before.Next() == 6u); // 몬스터 2

    ToyRng shared{3};
    assert(shared.Next() == 0u); // 몬스터 1
    assert(shared.Next() == 1u); // 이펙트가 한 번 소비
    assert(shared.Next() == 6u); // 전리품이 밀림
    assert(shared.Next() == 15u); // 몬스터 2도 밀림

    ToyRng gameplay{3};
    ToyRng visuals{7};
    assert(gameplay.Next() == 0u); // 몬스터 1
    assert(visuals.Next() == 4u);  // 이펙트 1
    assert(visuals.Next() == 5u);  // 이펙트 2
    assert(gameplay.Next() == 1u); // 전리품
    assert(gameplay.Next() == 6u); // 몬스터 2
}
```

위 예제의 상태는 `0~15`로 순환하므로 예측하기 쉽고 주기가 짧습니다. 게임에서는 검증된 PRNG를 사용해야 합니다. 예를 들어 Melissa E. O'Neill이 **2014년** 발표한 PCG 계열은 상태 전이와 출력 변환을 결합합니다. 원저자는 [최소 C 구현](https://www.pcg-random.org/download.html)과 시드 초기화·범위 변환까지 제공하는 라이브러리를 공개했습니다. 단순한 수식 예제를 그대로 PCG라고 부르지는 않습니다.

실제 구현에서 재현성을 원한다면 **알고리즘 이름과 버전, 스트림별 시드 또는 상태, 호출 순서**를 함께 기록해 두는 편이 안전합니다. 같은 이름의 엔진 API라도 버전이 달라지면 동일한 내부 수열까지 보장하는 것은 아닙니다.

## 엔진에서는 어떻게 적용할까요?

**Godot 4.5**의 `RandomNumberGenerator`는 인스턴스마다 `seed`와 `state`를 가질 수 있습니다. 아래 코드는 게임 로직과 장식 연출의 난수를 별도 인스턴스에서 생성하는 **실제 GDScript API 예제**입니다. 위 장난감 수열과 출력 숫자는 일치하지 않습니다.

```python
extends Node

var gameplay_rng := RandomNumberGenerator.new()
var visual_rng := RandomNumberGenerator.new()

func _ready() -> void:
    gameplay_rng.seed = 1001
    visual_rng.seed = 2002

func choose_enemy_index() -> int:
    return gameplay_rng.randi_range(0, 2)

func choose_spark_index() -> int:
    return visual_rng.randi_range(0, 3)
```

GDScript 코드를 단색 의사 코드가 아닌 실제 코드로 구분해 두었습니다. 두 함수의 호출 빈도가 서로 달라도 상대 스트림의 상태는 변하지 않습니다. 다만 **Godot 공식 문서는 현재 PCG32를 사용한다고 설명하면서도 내부 알고리즘은 구현 세부 사항이므로 버전 간 수열 호환에 의존하지 말라고 명시**합니다. 엔진 버전 간 재생 파일을 호환해야 한다면 알고리즘을 프로젝트에서 고정하거나 난수 결과 자체를 로그로 저장해야 합니다.

게임 리플레이, 네트워크 롤백, 절차적 월드 생성에서는 특히 다음을 분명히 해야 합니다.

- **전체 시작만 다시 재생**한다면 스트림 초기 시드, 로직 실행 순서, 사용한 난수 알고리즘을 고정합니다.
- **중간 지점에서 이어서 재생**한다면 초기 시드만이 아니라 그 시점의 스트림별 상태도 저장합니다.
- **멀티스레드에서 공유 스트림을 호출**하면 실행 순서에 따라 소비 순서가 달라질 수 있으므로, 작업별 스트림이나 결정된 호출 순서를 사용합니다.
- **최종 위치까지 동일해야 한다면** 난수 밖의 부동소수점 연산 순서·프레임 갱신·물리 연산 등도 별도로 결정론을 검사해야 합니다.

스트림을 너무 잘게 나누면 시드·상태 관리가 복잡해집니다. 반대로 전역 생성기 하나는 편리하지만 시각 효과와 게임 규칙이 얽힙니다. 실무에서는 적어도 **게임플레이 판정과 시각·음향 연출**을 구분하는 것부터 시작해 보세요.

## 오늘 얻어갈 것

처음 질문의 답은 **'같은 시드'가 '같은 호출 경로'까지 보장하지 않기 때문**입니다. 동일한 수열을 만들더라도 중간에 다른 시스템이 한 번 소비하면 이후 게임 결과가 밀립니다.

디버깅할 때는 난수 값만 출력하지 말고 **호출한 시스템, 스트림 ID, 호출 순번, 시드/현재 상태**를 같이 기록해 보세요. 위 C++17 예제로 호출 순서를 하나 삽입했을 때 값이 어떻게 달라지는지 확인하고, 실제 엔진에서는 각 생성기 인스턴스가 독립적인 상태를 가졌는지 살펴보세요. 리플레이를 복원하는 기능이라면 시드뿐 아니라 **스냅샷 시점의 PRNG 상태**가 복원되는지도 테스트해 보시면 좋겠습니다.
