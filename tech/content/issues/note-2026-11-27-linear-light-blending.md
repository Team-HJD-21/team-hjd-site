# 흰색을 절반만 섞었는데 왜 회색이 너무 어두울까요?

겜붕이의 노트 · by TeamHJD

## 투명한 흰색 이펙트를 검은 배경에 올려 봅시다

검은 배경에서 흰색 연기 이펙트의 알파를 0.5로 설정했습니다. 흰색이 내는 빛의 절반만 섞인 회색을 기대했는데, 화면에는 생각보다 어두운 회색이 나타납니다. 같은 셰이더를 다른 프로젝트에서 사용하면 결과가 더 밝아지기도 합니다. 색을 섞는 수식은 같아 보이는데 왜 이런 차이가 생길까요?

오늘은 RGB 채널의 숫자가 의미하는 빛의 양부터 살펴봅니다. 예제는 불투명한 검정 배경 위의 흰색 한 픽셀입니다. 조명, 톤 매핑, HDR, 후처리는 제외하고 SDR sRGB 출력만 가정합니다. RGB 세 채널은 같은 값이므로 하나만 계산해도 됩니다.

## 저장된 숫자와 빛의 양은 다릅니다

**선형 광량(Linear Light)**은 RGB 채널 값을 두 배로 올리면 해당 채널의 상대적인 빛의 세기도 두 배가 되는 표현입니다. 반면 일반적인 SDR 색상 텍스처에는 **sRGB**라는 색 공간의 비선형 인코딩 값이 들어갑니다. 낮은 광량에 더 촘촘한 코드 값을 배분할 수 있어 제한된 비트 수를 활용하는 데 유리합니다. sRGB는 단순히 감마 2.2 제곱으로 정의된 공간이 아니며, 원색과 백색점도 규정합니다. 오늘 관심사는 그중 전달 함수(Transfer Function), 즉 선형 광량과 저장값 사이의 변환입니다.

sRGB 값 S와 선형 값 L이 0~1에 있을 때 변환식은 다음과 같습니다. [W3C CSS Color 4의 2026년 10월 27일 후보 권고 초안](https://www.w3.org/TR/2026/CRD-css-color-4-20261027/#color-conversion-code)은 동일한 sRGB 전달 함수의 변환 예제를 제공합니다. 웹에만 적용되는 수식이 아니라 sRGB 값의 의미를 설명하기 위한 자료입니다.

```text
sRGB → 선형
S ≤ 0.04045 : L = S / 12.92
그 외        : L = ((S + 0.055) / 1.055)^2.4

선형 → sRGB
L ≤ 0.0031308 : S = 12.92 × L
그 외          : S = 1.055 × L^(1/2.4) - 0.055
```

검정의 0과 흰색의 1은 변환해도 그대로이지만, 가운데 값은 다릅니다. sRGB 0.5를 역변환하면 선형 광량은 약 0.214입니다. 반대로 선형 광량 0.5를 sRGB에 저장하려면 약 0.735가 필요합니다.

![가로축은 sRGB 값, 세로축은 선형 광량이며 0.5와 0.735의 대응 관계를 보여주는 곡선](assets/srgb-transfer.svg)

*직접 만든 개념도. 두 축은 0~1이며 전달 함수로 계산한 곡선과 두 대응점을 표시했습니다. 점선 대각선은 값이 그대로 비례할 때의 기준입니다.*

## 같은 알파 0.5를 두 가지 방식으로 계산합니다

**알파 블렌딩(Alpha Blending)**은 새로 그리는 색과 이미 렌더 타깃에 있는 색을 합성하는 과정입니다. 여기서는 곱셈이 적용되지 않은 원본 RGB(스트레이트 알파)를 사용하며, 알파가 1인 검은 배경 위에 흰색을 올립니다. RGB 채널의 블렌딩 식은 다음과 같습니다.

```text
out = src × alpha + dst × (1 - alpha)
```

알파는 광량의 sRGB 인코딩 값이 아니라 합성에 사용할 가중치입니다. 따라서 알파 자체를 sRGB 디코딩하지 않습니다.

먼저 인코딩된 sRGB 숫자끼리 섞으면 1 × 0.5 + 0 × 0.5 = 0.5가 됩니다. 8비트로 저장하면 약 128입니다. 이 값을 sRGB 화면에서 해석하면 선형 광량은 약 0.214에 불과합니다.

이번에는 색을 선형으로 해석한 뒤 섞습니다. 선형 흰색 1과 검정 0의 혼합은 똑같이 0.5입니다. 그러나 이 결과는 선형 값이므로 화면 저장 전에 sRGB로 인코딩합니다. 약 0.735, 8비트로 반올림하면 188입니다.

| 비교 | sRGB 숫자에서 혼합 | 선형 광량에서 혼합 |
| --- | --- | --- |
| 블렌딩 결과 | sRGB 0.5 | 선형 0.5 |
| 출력 sRGB | 0.5 | 약 0.735 |
| 8비트 RGB | 128, 128, 128 | 188, 188, 188 |
| 양자화 전 상대 선형 광량 | 약 0.214 | 0.5 |

![동일한 검정 배경과 흰색 알파 0.5에서 나온 128 회색과 188 회색의 비교](assets/blend-comparison.svg)

*직접 만든 비교도. 두 회색은 계산된 8비트 sRGB 코드 값으로 표현했습니다. 실제 엔진 캡처가 아니며 모니터 설정에 따라 보이는 밝기는 달라질 수 있습니다.*

두 방식은 블렌딩 수식 자체가 다르지 않습니다. 같은 수식을 어느 표현에서 적용했는지가 다릅니다. 물론 모든 색 보간을 선형으로 해야 한다는 뜻은 아닙니다. 아트 디렉션을 위해 특정 색 공간에서 그라데이션을 설계할 수 있습니다. 여기서 다루는 것은 빛의 선형 합성을 의도한 렌더링입니다.

## C++17로 숫자를 재현해 보겠습니다

다음은 0~1 범위의 채널 값과 불투명 배경을 가정한 독립 실행형 C++17 예제입니다. 실제 엔진 API가 아니라 전달 함수와 합성 결과를 확인하는 참조 코드입니다.

```cpp
#include <cmath>
#include <iostream>

double Decode(double s)
{
    return s <= 0.04045 ? s / 12.92
        : std::pow((s + 0.055) / 1.055, 2.4);
}

double Encode(double l)
{
    return l <= 0.0031308 ? 12.92 * l
        : 1.055 * std::pow(l, 1.0 / 2.4) - 0.055;
}

double Blend(double src, double dst, double alpha)
{
    return src * alpha + dst * (1.0 - alpha);
}

int main()
{
    const double src = 1.0, dst = 0.0, alpha = 0.5;
    const double wrong = Blend(src, dst, alpha);
    const double linear = Blend(Decode(src), Decode(dst), alpha);
    const double correct = Encode(linear);

    std::cout << std::lround(wrong * 255) << '\n'
              << std::lround(correct * 255) << '\n';
}
```

예상 출력은 아래와 같습니다. 8비트 변환은 가장 가까운 정수로 반올림한 예제이며, 실제 렌더 타깃의 양자화나 디더링은 별도입니다.

```text
128
188
```

실제 GPU에서 이 함수를 매 픽셀마다 수동 호출할 필요는 없는 경우가 많습니다. Direct3D의 sRGB 형식 리소스 뷰처럼 그래픽 API와 하드웨어가 제공하는 변환을 이용할 수 있기 때문입니다.

## 엔진에서 어느 경계가 변환을 담당할까요?

Unity 6.0의 Linear 색 공간에서 `TextureImporter.sRGBTexture`는 색상 텍스처의 샘플링 시 sRGB 값을 선형 값으로 해석하도록 설정하는 API입니다. [공식 TextureImporter 문서](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TextureImporter-sRGBTexture.html)를 참고하면 색을 저장하는 텍스처와 수치 데이터를 저장하는 텍스처를 구별해야 하는 이유가 드러납니다.

예를 들어 알베도처럼 색을 저장하는 일반 SDR 텍스처는 sRGB로 가져오는 것이 일반적입니다. 반대로 러프니스나 마스크에 저장된 0.5가 실제 매개변수 0.5를 뜻한다면 이 값을 0.214로 바꾸면 안 됩니다. 데이터 텍스처는 제작 규약에 따라 sRGB 변환을 끄는 것이 중요합니다. 하나의 텍스처에 여러 데이터를 패킹할 때도 채널의 의미와 하드웨어의 RGB 변환 규칙을 확인해야 합니다.

출력 쪽에서는 [Microsoft의 Direct3D 10/11 Output-Merger 문서](https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d10-graphics-programming-guide-output-merger-stage)가 sRGB 렌더 타깃에서 기존 색을 선형으로 바꾸어 혼합하고 결과를 다시 인코딩하는 동작을 설명합니다. 다만 D3D11의 낮은 기능 수준 9_3 이하 등에는 예외가 있으므로 [블렌드 상태 문서](https://learn.microsoft.com/en-us/windows/win32/api/d3d10_1/ns-d3d10_1-d3d10_blend_desc1)도 함께 참고하세요. 선형 부동소수점 HDR 타깃에서는 중간 결과를 선형으로 유지하고 최종 출력 단계의 변환을 별도로 담당할 수 있습니다.

프로젝트의 색 공간이 Linear라고 해도 모든 사용자 정의 렌더 타깃과 셰이더의 입출력이 자동으로 올바르다는 보장은 없습니다. 하드웨어가 이미 디코딩한 텍스처를 셰이더에서 다시 디코딩하거나, 선형 출력이 필요한 타깃에 sRGB 값을 수동 인코딩한 뒤 쓰면 이중 변환이 발생할 수 있습니다.

작은 테스트 씬에서 검정 배경과 흰색 투명 쿼드를 준비하고 후처리를 끈 뒤, 프레임 디버거나 GPU 캡처에서 다음을 확인해 보세요. 샘플링하는 텍스처 뷰의 sRGB 여부, 셰이더 출력의 색 표현, 블렌드 팩터, 렌더 타깃 뷰의 형식, 최종 출력 변환입니다. 중간 선형 타깃의 0.5와 최종 sRGB 타깃의 약 0.735는 같은 광량을 가리킬 수 있습니다. GPU 캡처 도구가 원시 저장값과 디코딩된 표시값 중 무엇을 보여주는지도 구분해야 합니다.

색 공간을 바꾸면 기존 아트와 조명, 투명 이펙트의 인상이 달라질 수 있습니다. 무조건 변환을 추가하는 대신 파이프라인의 어느 단계가 변환을 책임지는지 기록하고 비교하는 것이 좋습니다.

## 오늘 얻어갈 것

흰색을 절반 섞었는데 너무 어두워 보이는 이유는 0.5라는 sRGB 코드가 빛의 절반을 의미하지 않기 때문일 수 있습니다. 오늘 예제에서 sRGB 숫자로 직접 혼합한 결과는 128, 선형 광량을 합성한 뒤 인코딩한 결과는 188이었습니다. 이는 특정 엔진의 측정값이 아니라 전달 함수로 계산한 결과입니다.

코드에서는 색과 수치 데이터를 구분하고, 엔진에서는 텍스처의 sRGB 설정과 렌더 타깃 형식을 확인해 보세요. 프레임 캡처에서는 픽셀 셰이더 출력부터 최종 출력까지 어떤 경계에서 변환되는지 따라가면, 같은 색과 알파가 다른 화면을 만드는 이유를 찾을 수 있습니다.
